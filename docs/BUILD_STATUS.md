# MEF Platform — Build Status

Source: `/docs/INVENTORY.md` (file-level inventory + Overlaps analysis), plus a small number of targeted follow-up reads cited inline where they go beyond what INVENTORY.md already established. Scope is bounded to the assessment / onboarding / welcome / cross-assessment-intelligence subsystem, which is what INVENTORY.md documented in depth — this is not a build-status audit of Food Lens, Movement, Wearables, etc. as standalone features. No application code was written or changed to produce this document.

## Direction of travel

**`lib/assessment-runtime/` + `lib/assessment-foundation/` (the Unified Adaptive Assessment Runtime) is the chosen shared foundation for all assessments going forward.** The older, per-assessment engines are legacy — candidates to be migrated onto the unified runtime over time, not systems to keep building out in parallel indefinitely.

This is not an inference — it's what the schema's own migration states. `supabase/migrations/00000000000098_unified_assessment_foundation.sql`'s header comment: *"a reusable question/section/assessment schema that future assessments (Four Doctors v2, HAQ, WBSA, Breathing, Nutrition, Primal Pattern, etc.) can opt into instead of inventing a new bespoke table set each time."* It explicitly names Four Doctors, HAQ, and Primal Pattern — three of today's legacy engines — as intended future migrants onto this schema, not permanent parallel systems.

- **Schema**: `unified_assessment_definitions`, `unified_assessment_sections`, `unified_assessment_questions` (`supabase/migrations/00000000000098_unified_assessment_foundation.sql`), `unified_assessment_sessions`, `unified_assessment_answers` (`supabase/migrations/00000000000099_unified_assessment_runtime.sql`).
- **Logic**: `lib/assessment-foundation/{repository,adaptive,index}.ts` (content read layer), `lib/assessment-runtime/{data,conditions,session,findings,types,index}.ts` (session/answer/branching/findings engine).
- **First (and, as of this document, only) adopter**: WBSA — content seeded by `supabase/migrations/00000000000100_wbsa_schema_extensions.sql` and `00000000000101_wbsa_content.sql`, served by `components/wbsa/WbsaTaker.tsx` and `app/assessments/wbsa/{page,take/page,results/[sessionId]/page}.tsx`.
- **Not yet migrated**: the generic points-scored engine (CHEK HLC1 / Four Doctors / Short-HAQ), Primal Pattern, Body Assessment, and the Onboarding adaptive engine — see 🟡 below for each.

### 6. Two coexisting welcome/first-run flows
- **What exists**: `app/welcome/{page,WelcomeFlow}.tsx` + `lib/welcome/{eligibility,goals}.ts` (four-screen welcome experience, goal selection) sits *in front of* the pre-existing `app/onboarding/{page,OnboardingIntro,ConsentForm,OnboardingFlow,OnboardingForm}.tsx` consent → onboarding progression, gated by `WELCOME_FLOW_ENABLED = true` (`lib/welcome/eligibility.ts`) and a per-profile `welcome_flow_eligible` flag set only for new signups (migration 85's `handle_new_user` trigger).

## Open decisions

**1. Which Four Doctors results route is canonical?**
Resolved in code, but the underlying question of *whether this is the intended long-term shape* is still open. `app/assessments/four-doctors/results/[assessmentId]/page.tsx`'s own header comment states it's "a static route... Next.js resolves ahead of the generic dynamic `app/assessments/[questionnaireId]/results/[assessmentId]/` route for this one exact path" — and `components/assessments/AssessmentTaker.tsx` (line ~301, ~322) redirects to `/assessments/${slug}/results/${id}`, which for the Four Doctors slug lands on that dedicated route by Next.js's static-over-dynamic precedence. So **the dedicated route is canonical today, by routing mechanics, not by an explicit decision recorded anywhere.** The generic route remains canonical for CHEK HLC1 and Short-HAQ only. Open question: should the generic `[questionnaireId]/results` route be updated to explicitly acknowledge it never serves Four Doctors (dead-code clarity), or should Four Doctors eventually be folded back into the generic route like its two siblings?

**2. Does the welcome flow replace the onboarding-consent path, or stay conditional?**
Confirmed conditional, not a replacement, by reading `app/actions/welcome.ts`: `completeWelcomeFlow()` redirects to `/` and lets `app/page.tsx`'s existing `hasCompletedConsent()` / `onboarding_submissions` checks run exactly as before — a brand-new member goes welcome → (back through the hub) → onboarding, not welcome-instead-of-onboarding. Gating is by `welcome_flow_eligible`, set only for new signups (migration 85), so existing members never see `/welcome` at all and go straight to consent/onboarding as before. Open question: is a permanent two-population split (new members: welcome + onboarding both; existing members: onboarding only) the intended end state, or is welcome meant to eventually absorb what `app/onboarding/{OnboardingIntro,ConsentForm}.tsx` currently do for new members — at which point those two files would become dead code for the new-member path (still load-bearing for the existing-member path, since they're not eligibility-gated the way welcome is)? Nothing in the code states an intended end state either way.

## Voice guidance regression from the bug-fix pass above, found and fixed (2026-07-26)

The previous entry's reproducibility-gate bug fixes silenced spoken guidance — reported from real-phone testing. Root cause diagnosed (not just patched):

- **The actual bug**: the main per-frame validation `useEffect` in `CameraCapture.tsx` had `tilt` (the whole object) in its dependency array. `tilt` is a fresh object literal computed at the top of every render (`evaluateCameraTilt(...)` or the manual-fallback branch), never memoized — so React saw it as "changed" after every render, including renders the effect's OWN `setValidation`/`setStableForMs` calls caused. This re-ran the effect in a tight loop, and `useGuidedVoice.speak()` always cancels whatever utterance is currently playing before starting a new one — so every cue was technically spoken (the code path ran) but never audible, since each call canceled the previous one before the browser could finish it. Fixed by depending on `tilt.ok`/`tilt.message` (stable primitives) instead of the object.
- **Caught the same class of bug while adding the new stuck-detector effect**: its dependency array initially included the whole `guidedVoice` object (also a fresh object every render — `useGuidedVoice` only memoizes its individual functions via `useCallback`, not the object it returns). Fixed to depend on `guidedVoice.speak` specifically before it ever shipped.
- **The 20s stuck message is now spoken**, not just displayed (`StuckGuidance.tsx`'s text) — a direct `guidedVoice.speak()` call on the rising edge of stuck mode, using whatever the main validation effect most recently determined was blocking (`latestBlockingMessageRef`), routed through the same `markSpeechStarted`/`markSpeechEnded` bookkeeping the rest of the guidance pipeline uses so the routine per-frame correction cadence can't cancel it mid-sentence.
- **Fixed a z-index bug that would have defeated the recovery path**: the stuck-mode overlay (`z-30`, full-frame) sat above the existing "Tap once to enable voice guidance" recovery banner (`z-20`) — once 20s passed with audio blocked, the recovery tap would have become permanently unreachable underneath it. Both the "blocked" and "unavailable" voice banners are now `z-50`, above `StuckGuidance`'s `z-30`, so the recovery tap stays reachable no matter how long the member has been stuck.
- **New explicit audio-unlock prep screen**: the `preparation` intro step (first screen after Welcome) now has a real, tap-triggered "Enable voice guidance" button — not just the existing silent `primeBrowserSpeechSynthesis()` priming — that speaks an actual audible confirmation line and shows live feedback from `guidedVoice.status` ("Voice guidance is working," or "We couldn't confirm audio played — check your volume/silent switch" if the mobile-autoplay unlock genuinely fails even from a real tap). Shares the same `'assessment-guidance'` id as `CameraCapture.tsx`'s own instance so the two coordinate through the existing `playbackRegistry` rather than talking over each other. Non-blocking — same "advisory, not required" posture as the existing motion-sensor permission screen, since on-screen text remains a working (if secondary) fallback for a member with no speaker.
- **Confirmed unaffected/working**: the countdown (`READY_PROMPT`/`TAKING_PHOTO_PROMPT`), the step-intro script, and every other correction cue all go through the same `guidedVoice.speak()` call the fixed effect now reaches at its normal (not runaway) cadence — no separate fix needed for those once the dependency bug was corrected.

## Real cross-variable correlation engine — replaces the rule-based `crossAssessmentCorrelations.ts` (2026-07-26)

`lib/intelligence-engine/crossAssessmentCorrelations.ts` was named for what it should have done, not what it did: it checked whether both halves of five hand-written pairings had an active registry finding and printed a canned sentence — no statistical calculation anywhere in it. This replaces it with `lib/correlation-engine/`, which actually looks at a member's own daily numbers over time.

- **What it computes**: for one member, whether two of her tracked daily variables move together — real Spearman rank correlation (`lib/correlation-engine/stats.ts`), never Pearson, since every input is an ordinal scale (1-5 ratings, 0-5 pain, bucketed sleep-duration, binary flags).
- **Candidate pairs are data, not code** (`correlation_candidate_pairs`, migration 105): 18 pairs seeded from `MEF-driver-library-v1.md`'s driver list and goal-weighting table, restricted to the subset that maps onto a column that actually exists today (`daily_checkins` + `wearable_daily_metrics`) — most of the driver library (workstation load, footwear, caffeine/alcohol timing, meal regularity, training volume, posture-assessment findings) has no daily-loggable source anywhere in the schema yet, so those pairs are left out rather than faked. Two seeded pairs (`sleep_quality_stress`, `digestion_stress`) are the direct successors of two of the old file's five rules; the other three old rules paired a daily variable against a posture-assessment registry finding, which isn't a daily-paired time series and has no equivalent here — retired, not migrated. More pairs can be added with a plain `insert`, no deploy.
- **Goal-scoped, reusing last week's `member_goal_selections`** (`lib/correlation-engine/data.ts`'s `candidatePairsForGoals`): "an outcome she cares about paired with a driver weighted for that goal" is implemented by filtering candidate pairs to the member's own recorded goals (`fetchLatestMemberGoalSelection`, the table the welcome-flow-goals build above just made real) — a member with no goals on file gets every active pair instead of none.
- **Lag**: same-day and next-day only, tested independently, the stronger `|rho|` reported (`lib/correlation-engine/evidence.ts`'s `evaluatePair`).
- **Real evidence gate, one place, named constants**: `MIN_PAIRED_OBSERVATIONS = 21`, `MIN_SPAN_DAYS = 21` (both `evidence.ts`), `EFFECT_SIZE_FLOOR = 0.3` (Cohen's conventional "medium" correlation effect size — an effect-size floor, not a significance test), plus a variation guard (`stats.ts`'s `hasSufficientVariation`, `MAX_MODE_SHARE = 0.85` — no single value may be more than 85% of a series). A pair failing any of these never surfaces as a measurement, only as `insufficient_data`.
- **Split-window stability**: history is split in two by date; each half must independently clear the effect-size floor with the same direction as the full-history result, or `splitWindowAgreement` is `false` — a half with too little data to test at all (`MIN_SPLIT_WINDOW_OBSERVATIONS = 8`) counts as not-yet-provable, never as agreement by default.
- **Never interpolates**: `lib/correlation-engine/pairing.ts` pairs two variables only on the exact calendar date(s) a lag calls for — a missing check-in day breaks that one pair, nothing is carried forward or guessed.
- **Feeds the existing three-tier system, not a parallel one**: `member_pattern_states` (migration 93) widened to accept a fifth `signal_kind`, `'correlation_finding'` — the write path itself (`upsertMemberPatternState`) was already fully generic over `signal_kind`, so no change was needed there. `lib/correlation-engine/classify.ts` is a new, separate classifier (mirroring `lib/longitudinal-intelligence/signalState.ts`'s occurrence/tier structure and importing its `ESTABLISHED_MIN_SPAN_DAYS`-equivalent constant and `MIN_CONFIDENCE_TO_PERSIST`, but **not editing that file**, per the request) — a correlation is recomputed fresh from full history every scheduled run, so occurrence count grows via the same "same relationship reconfirmed on consecutive runs" mechanism `classifyCheckinMetricSignal` already uses, not a discrete event chain. `established_pattern`/tier 3 requires occurrence ≥ 3 **and** span ≥ 21 days **and** confidence ≥ 0.55 **and** split-window agreement, together — the same all-conditions-at-once structure `classifyRegistryFindingSignal` uses for its own established gate. `lib/longitudinal-intelligence/copy.ts` (the three-tier coaching language) is reused verbatim, unedited — it keys only on `state`/`tier`, never `signal_kind`.
- **This engine's own evidence record** (`member_correlation_findings`, migration 105): one row per (member, pair) — lag, direction, rho, observation count, span, split-window agreement, resulting tier, computed timestamp — upserted by `lib/correlation-engine/data.ts`. Separate from `member_pattern_states` on purpose: this is "what did we compute this run," the pattern-states row is "what the coaching layer sees" — the same split registry findings and check-in metrics already have between their own source data and the shared state ledger.

## Coaching Insights (`/insights`) — four display-bug fixes (2026-07-26)

Confirmed the task's own assumption first: all four were presentation faults, not engine faults. The pattern engine, trend engine, three-tier language (`lib/longitudinal-intelligence/copy.ts`), and correlation engine are all completely untouched — every fix is in how an already-correct classification gets composed into text or shown/hidden on the page.

- **Bug 1 — bare tier sentences with no subject** (`"We noticed this once."` / `"You mentioned this once."` / `"We don't have enough information yet to say much about this."`, each with no nameable subject): root cause was that `app/actions/longitudinalIntelligence.ts`'s `getMyLongitudinalPicture()` mapped straight to `describeSignalForMember(signal)` and discarded the rest of the signal — `copy.ts`'s sentence templates were never designed to carry a subject themselves, because Case View (`lib/case-view/findings.ts` → `components/case-view/FindingsList.tsx`) already renders the subject as a separate bold label alongside that same sentence; embedding a subject inside `copy.ts` itself would have duplicated it there. Fixed at a new layer instead: `lib/longitudinal-intelligence/picture.ts` (new file, not in the shared barrel, zero other importers) composes `{ subject, sentence }` pairs using `topicLabelForSignal` (`lib/root-coaching-engine/topicLabel.ts`, reused unmodified — already the exact tool for turning a bare `WellnessMetricKey` or a registry finding's own human label into a short subject) alongside the unmodified `describeSignalForMember`. When `topicLabelForSignal` falls back to its own generic `'this area'` placeholder (a signal with no real nameable subject), the item is dropped entirely rather than rendered — per the task's own instruction, an empty slot beats a sentence with a hole in it. `app/insights/page.tsx` now renders each line as `{subject} — {sentence}` with the subject bolded.
- **Bug 2 — "Your Next Best Step" names nothing and links nowhere**: the Root Router's `RootRouterOutcomeView` (`lib/investigation-engine/routerOutcome.ts`) already carries a populated `investigation: { displayName, route }` for exactly the two outcomes whose message claims "a specific area worth exploring" (`focused_investigation`, `reassessment`) — it was simply never read. `getMyLongitudinalPicture()` now returns `nextBestStep: { message, investigation } | null` via a new `nextBestStepView()` (also in `picture.ts`); the page links `investigation.displayName` to `investigation.route` (same `Link ... as Route` pattern `components/dashboard/WhatWereNoticingCard.tsx` already uses for the identical `RecommendedInvestigationView` shape). If one of those two outcomes ever had no investigation attached, the whole card is suppressed rather than shown with a dangling claim — defensive, since by construction in `routerOutcome.ts` this can't currently happen.
- **Bug 3 — the page contradicted itself** ("Nothing to share yet" sitting directly above a "Your Longitudinal Picture" section that then said things): `insights.length === 0` (the 5-generator Coaching Insights Engine) and the Longitudinal Picture (a completely independent generator over the same underlying signals) were rendered from two unrelated conditionals, so a member with zero Coaching Insights but a real longitudinal signal saw both. `app/insights/page.tsx` now computes `pictureHasContent` (true if any of the four groups or `nextBestStep` is non-empty) and only shows the "Nothing to share yet" card when **both** `insights.length === 0` and `!pictureHasContent` — i.e., only when there is truly nothing anywhere on the page to show.
- **Bug 4 — "1 check-in so far, over 9 days" read like a glitch**: this exact phrase does not exist anywhere on `/insights` — a full-codebase search found it only in `components/case-view/CaseEmptyState.tsx` (Case View, `/case`). Flagged the conflict against this task's own "don't touch Case View, it's out of scope" instruction; the user confirmed the scope note doesn't cover this specific phrasing bug and asked for it fixed in place. Fixed via a new pure `buildStillBuildingSentence()` (`lib/case-view/emptyState.ts`) that leads with elapsed time ("It's been 9 days since you started, and you've logged 1 check-in so far...") instead of the old `"{count} so far, over {days} days"` construction that visually resembled a broken template. Same real numbers, never invented or rounded — just reordered so a low count over a long span reads as an honest fact instead of a mismatch. `CaseEmptyState.tsx` calls this one function instead of inlining the string.
